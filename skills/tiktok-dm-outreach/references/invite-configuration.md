# 批量合作邀请配置

适用于用户已确认的紫鸟联盟邀约流程。教学、读取商品、制作配置面板不自动授权发邀约或删除草稿中的达人；当前任务明确授权后执行，不逐条重新确认。邀请文本须使用用户当次确认内容，不能沿用页面旧草稿。

每轮先选择店铺，再由代理通过控制接口建立或复用该店铺可操作的紫鸟窗口，进入查找达人页，再由用户在这个窗口设置原生条件；设置后保持同一窗口和有效页面目标，不刷新、重开或重置。对话确认本轮快速筛选/内容复核、PPS和邀约配置，文字确认有效；邀请文本、紫鸟私信、商品佣金、样品方式按当轮确认，同轮不重复问。完整先后顺序以`SKILL.md`的“紫鸟找达人完整顺序”为准。

连接按[四点优化](ziniao-connection.md)执行，店铺身份、页面和控制目标按当次选店分别核对；商品目录、佣金、话术和本轮配置不跨店沿用，不在连接阶段提前遍历商品或检查旧邀约。

## 入口与字段

1. 核对完整账号名单及50/50计数，点“批量邀请”。
2. 选“创建新邀请”→“仅佣金”→“邀请”，进入创建页。此入口点击不代表已发送。
3. 名称为`自动批MMDD（语言）N`，如`自动批1020（英语）1`（N为当天批次正整数），最多30字符，名称同用UTF-16计数口径。
4. 日期统一读取**紫鸟后台显示的店铺日期**，用于命名、截止日期及当月重叠判断；不替换为电脑日期或自行选定的美国时区。无法可靠读取时待核对，不猜测。
5. 有效截止日期为店铺当天**加20个日历日**：10月20日→11月9日，10月19日→11月8日。不能用“当天第1天”算成加19日；处理跨月、跨年和闰年。
6. 店铺日期、语言、名称、截止、电子邮箱、电话均由代理处理，不让用户填写：语言跟随本次达人筛选条件，邮箱沿用紫鸟系统自带值，电话留空。面板只在可折叠的只读区域展示这些自动信息。缺少自动字段来源时代理在执行前读取，不用旧草稿值覆盖，也不阻塞用户先确认话术和商品配置。邀请文本最多500字符；按后台计数口径，当前已实测为JavaScript字符串长度（UTF-16），部分表情占2个单位。空白正文不能作为用户已确认内容。
7. 内容形式当前可选“带货视频”“带货直播”“暂无偏好”。

字段限制为现场快照，执行前核对当前控件。名称/正文显示实时计数，超长不截断后擅自发送。

## 连续填写与统一核对

按当轮已确认配置，连续填完邀请名称、截止日期、邀请正文、全部已选商品及各款标准/广告佣金，并设置内容形式及样品方式。商品数量以本次配置为准。填写期间不逐项返回、截图或重复回读整张表单；出现输入未生效或报错时，只处理受影响项。

全部填写完成后统一核对一次：名称与店铺日期、截止日期、正文及字符数、商品ID及数量、各款佣金和广告佣金开关、样品方式及内容形式；邮箱沿用系统值、电话留空。核对无误直接进入重叠处理，不把同一批字段拆成多轮检查。重叠处理后只核对变动的达人名单、实际人数及冲突状态；已核对且未改变的表单字段不重复全量检查。有当次发送授权时继续下一步。

## 开头的店铺选择

在配置面板最前提供店铺选择，选项来自`assets/store-catalog.json`中用户明确授权分享的店铺商品目录，或当前使用者自行补充的对应店铺目录。默认用`scripts/build_invite_panel.py --output <当前项目绝对路径>`生成带目录的面板。选择有目录的店铺后显示其真实商品图片，未同步的店铺显示“商品待同步”，按用户选择接通该店铺再读取商品。无权限或尚不知名称的店铺留待有权限者补充，不捏造目录。选择动作只切换本地面板；“接通所选店铺”回传连接请求，代理实际连接并核对店铺后才算就绪。

切换店铺时清空已选产品、佣金、两份正文及临时搜索；不同店铺使用独立目录、位置、轮次及批次。恢复草稿必须同时匹配面板轮次contextKey、storeKey、storeContextKey，不接受上轮或其他店铺的草稿。新轮不预填历史正文或佣金。

## 使用者自己的商品目录

共享目录已有所选店铺时，直接显示对应商品及图片，不要求新使用者重新录入。当前店铺未收录或需补充目录时，再执行以下初始化：

1. 从使用者已登录的紫鸟页面确认其当前店铺和可操作的联盟中心；仅有多个店铺且目标不明时补问目标店铺。原作者的店铺、会话、固定页面ID和电脑路径均不是默认值。
2. 打开本店铺“选择商品”→“添加商品”，读取全部实际分页或懒加载记录，按商品ID去重，记录名称、真实缩略图、当前价格、可选状态及页面可见的库存/样品等字段。核对已加载目录范围，不能将当前一页或“还能添加N件”当完整目录；确实无法读全时标明范围。
3. 在使用者自己的私有工作目录保存目录和图片，按店铺标识隔离。将本店铺目录注入空白 `assets/invite-config-template.html`，搜索结果与已选列表都显示对应ID的真实图片。缺图标记后补取，不能用另一店铺商品或占位图冒充完整目录。
4. 让当前使用者选择其产品，填写并确认本轮各款标准佣金、广告佣金、邀请文本、紫鸟私信及样品方式。商品来自当前所选店铺目录，具体选品、佣金和正文不预选；邮箱读取当前店铺系统值。后续由代理按已确认值填写后台。

初始化完成后，沿用下一节的商品位置索引加ID核对路径，不每轮扫描全目录。换店铺时换用独立的 `contextKey`、目录、位置索引及每日批次，不能从上一店铺恢复草稿；同店铺新一轮也要区分轮次确认。用户明确授权的店铺名称、商品ID/名称/图片和展示价格可以进入共享目录；其他目录、Cookie、凭据、邮箱、实际话术、佣金和轮次配置不进入共享包或公开仓库。

## 商品与佣金

打开“选择商品”→“添加商品”，先使用本店铺已记录的商品位置定位本轮已确认商品，核对行内商品ID和当前可选状态后直接添加；已有对应定位记录时，不重新遍历整份目录。每次成功找到本轮商品，更新私有定位索引：店铺标识、商品ID/名称、图片引用、当时页码/每页条数/行号或滚动区域、排序/筛选条件、观察日期与来源；未知项留空，不猜测。位置用于快速定位，以准确商品ID确认身份，不能按旧坐标盲点。位置变化或未找到时，改用商品ID/名称搜索并更新记录；仅首次同步完整选品面板或明确需要刷新目录时才读取完整分页。不要把“还能添加N件”误认成目录总数，也不沿用旧库存、价格或上轮佣金替代本轮确认。真实定位索引与图片只留私有项目，开源仅保存通用方法。

配置面板参考`assets/invite-config-template.html`：提供搜索、多选、分页及按商品ID绑定的逐行配置。底层模板的数据为空；使用`scripts/build_invite_panel.py`自动从共享`assets/store-catalog.json`注入店铺目录及新的面板轮次`contextKey`，不把底层空白模板作为分享使用入口。也可通过`--catalog`指定使用者自己的目录。每家店结构为`{key,name,storeId,expectedName,catalogStatus,products,shopDate,language,contactEmail,sourceDate,contextKey,batchNumber}`；`catalogStatus`取`ready/needs-sync/no-access`，未知ID留空，未命名的待补充数量用`pendingStoreCount`表示。`products`只属于该店；不要发布含本轮话术、佣金、邮箱或会话的副本。每款商品数据结构为`{id,name,priceText,sold,stock,status,addedDate,samplePaused,unavailable,imageData}`。contextKey区分店铺，恢复状态不能跨店铺；恢复草稿仅恢复用户填写项，日期/语言/系统邮箱重取当前来源，电话始终留空。执行时重新读取日期与校验商品可选性。

搜索商品列表和已选商品列表均显示按商品ID对应的真实缩略图。imageData可放当次授权浏览器截图中裁出的私有缩略图；核对图片与行内ID，不能用同名商品、占位图或错图替代。图片来源缺失/加载失败时明确标记缺图，不能声称图片齐全；待补齐后重验。用户明确授权的商品缩略图可放入共享目录；其他私有图片和带令牌链接不公开。图片不进入配置提交消息或保存的交互状态。

- 单次邀请最多100款。商品同名、截断或不同规格不能混用，以商品ID核对。
- 每款填标准佣金率；店铺广告佣金可独立开启/关闭，开启时填广告佣金率。当前两项输入提示均为1.00%–80.00%；面板校验该范围并保留至多两位小数。后台规则变化时更新约束，不自行设佣金。
- 后台商品选择框禁用时记录现状，不能伪造可选。若禁用仅因已在当前草稿选中，区分“已选”与“不可选”；其他禁用原因未核实时不猜。暂停样品也不能等同商品不可邀约。
- 广告佣金关闭不宣称广告订单佣金为0；具体沿用后台适用规则。

## 免费样品

“提供免费样品”开关独立选择。开启时有两种审批方式：

- **使用商品级别的样品设置**：沿用商品审批规则及限额；未设规则的商品需要手动审核。
- **批准此邀请中的所有人**：自动批准本邀请达人的**免费样品申请**，不是自动接受所有合作或消息。

不能替用户默认开启自动批准；面板初始可跟随当前已核对状态，提交时明确所选值。

## 重叠：按达人汇总后处理

每次打开或重开重叠弹框，先将分页设为50/Page，再读取旧邀请名称、对应完整账号和商品并遍历相关分页。50/Page表示每页50条重叠记录，不等于50位不同达人。同一达人可能有多个商品/旧邀约，不能把每行当不同达人。使用店铺日期判断所属月，并处理命名日期缺失、年份或记录歧义；不能可靠判定就标待核对。

| 旧邀请 | 对当前邀请的处理 |
|---|---|
| 名称为“自动批”且属于店铺当月，如当月10月的`自动批1019（英语）` | **从当前邀请名单移除该达人，保留旧邀请** |
| 不属于店铺当月，名称含“手动” | 移动至本次邀请 |
| 不属于店铺当月，名称不含“手动” | 移动至本次邀请 |
| 属于店铺当月，名称非“自动批”（包括“手动”和其他名称） | 移动至本次邀请 |
| 日期或身份无法判断 | 待核对，不猜测归属 |

### 集中记录、集中移除、统一移动（用户确认）

1. **先完整查看重叠列表并记录排除名单。** 按50/Page遍历相关分页，核对实际行数据已刷新；同一达人只要任一商品所属旧邀请命中“自动批＋店铺当月”，立即把其完整用户名加入去重后的排除名单。命中后无需为决定是否排除而继续判断该达人的其他商品，但仍继续查看列表，找齐其他需要排除的达人。可保存截图佐证，操作依据为准确账号名单。
2. **看完后点右上角叉号关闭弹框。** 不每找到一个人就退出删除再重开。返回“选择达人”列表，按排除名单集中移除这些达人；使用准确账号对应行的垃圾桶，页面支持准确批选时也可集中删除。这里只移除本次邀请名单，保留旧邀请与达人账号。
3. **删除完成后，再打开“解决重叠问题”。** 只核对名单与人数变化、已排除账号不再出现，以及重叠数据已经刷新；不重新逐条判断已完整查看且未改变的其余记录。原记录中日期或身份不明的项先核实，不把未查看的记录默认视为可移动。
4. **剩余冲突均可移动时统一处理。** 选择“将达人移动至此邀请”→“去解决”，如出现移动确认则继续确认，最后核对无冲突与实际剩余人数。先完成全部排除，再统一移动，避免交替逐人删除与移动。

50/Page是商品冲突行数。若标题所示达人总数与已读去重人数不一致，不能假定已看全而整体移动；先集中移除已确认的当月自动批达人，再重开读取剩余冲突，补齐排除名单，确认所有剩余记录可移动后统一处理。不以旧页码已变化代替实际行数据已刷新。


移除后刷新名单、重叠状态及剩余人数，最终剩多少就按多少人邀约及分享私信，不回头重新找人补齐；用户以20人说明此行为，20不是固定批量或每轮目标。不能仍报告原人数，也不修改已定产品/日期来绕过冲突。名称仍按`自动批MMDD（语言）N`及执行时店铺日期自动填写。公共模板中的冲突函数只是辅助分类，不会自动操作后台。

## 配置提交与真实发送

执行范围按`SKILL.md`的“完整一轮的执行与完成条件”判断；本轮已授权的连续执行不会被面板的配置提示撤回。同轮恢复只补缺项并接未完成阶段，不从头准备、不重复发送已完成阶段。

面板“确认本次邀约配置”把邀请文本、独立的紫鸟私信、产品ID/佣金、样品方式及自动字段处理规则回传对话（已读到的日期/语言可附带，只作当次快照）。按钮只提交配置；已有本轮完整流程的执行指令且配置齐全时，代理继续到邀约发送及紫鸟私信，不额外等待一个发送确认。正文分别保存为`message`和`ziniaoMessage`；配置包含私信流程时分别要求非空、分别计数和校验，不能把原邀请文本自动复制成私信。不得把填好字段、打开预览、点过入口或请求成功当作已发送。

实际发送按当次授权：表单字段按“连续填写与统一核对”集中检查一次；处理重叠后核对完整账号名单、实际人数与冲突结果，未改变的已核对字段不重复全量检查。提交成功后立即进入紫鸟私信并完成分享，再集中记录批次结果和实际人数，按下述规则直接整理是否完成；不在邀请成功与私信之间另开检查流程。未完成现场邀请提交和结果回读时，明确只验证了读取与本地面板，不声称完整自动化已跑通。

## 邀请成功后的紫鸟私信

这一步在紫鸟联盟后台完成，与原合作邀请的“邀请文本”及手机私信分别确认。用户教学截图中“发送邀请”模态框右侧正文显示`399/500`：已用399、上限500。面板独立提供“紫鸟私信”填写框、500上限及实时计数，初始留空，不采用页面自带模板或历史正文。面板暂按UTF-16计数；后台私信的表情、换行及用户名替换计数尚未实测，实际发送前核对当前控件的上限与计数，不能沿用原邀请正文的实测结论冒称私信计数已核验。若含用户批准的用户名变量，替换后逐人核对长度；超限不擅自删改话术。

在当次对象、内容与外发授权齐全时，按以下顺序执行：

1. 创建邀请页核对配置及重叠处理后的实际达人名单，点击底部“发送”一次。结果不明先查已保存邀请，避免重复提交。
2. 出现“合作邀请发送成功！”后，立即在同一成功页点“向达人发送消息”，继续完成私信；不先点“查看邀请”、重开邀请列表或为单独截图核验打断衔接。只进入这一步不能宣称已发送私信。
3. 在“发送邀请”模态框准确选择本次实际剩余达人，核对完整用户名及选中计数；不能继续假设50人，也不能重选已因当月冲突移除的达人。
4. 开启“Send message with invitation”，填入用户当次确认的**紫鸟私信**，核对预览、字数及邀请卡归属。平台预填内容或“使用模板”不代表用户确认。
5. 收件人、已确认正文和卡片均正确后点击“分享”一次。根据正常流程显示的批次结果简要记录并汇报是否完成，不再打开单个会话抽查、不排查消息数量限制、不增加截图检查。灰色不可选跳过，已出现的数量上限按用户接受的正常结果记录，不重发；真实阻塞如实汇报。

面板确认用于保存本轮配置；仅教学或只改配置时不外发。采用完整流程、本轮配置齐全且用户已有“开始/继续/跑完”等执行指令时，该指令包含上述“发送”和“分享”，不再重复确认，也不因旧面板或旧状态的未授权提示停下。以同轮较新的直接用户指令为准，用户明确缩小范围或暂停时遵守。原邀请正文未确认或紫鸟私信未确认时，不用另一份正文顶替。消息开关开启不等于消息已发；0位达人可选时记录跳过，不强选或重发。

手机私信及已读回复跟踪是后续独立步骤，按任务范围、身份核验与台账执行，不因合作邀请或后台私信完成而冒称已发手机私信、已读或已建立持续监控。
